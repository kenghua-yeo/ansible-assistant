# Conventions

Distilled from the existing collections under `collections/` (`cloud.aws_ops`,
`cloud.aws_troubleshooting`, `infra.windows_ops`, and any others added
later - see `catalog.md` for the current list). This whole directory is a
reusable template: the same `/spec` -> `/build` cycle runs here repeatedly
for unrelated automation requests over time. Two trees, two rules:

- **`collections/` is read-only reference.** `/spec` and `/build` only
  ever *read* from it - conventions to follow, real code to model new
  roles on. Neither skill writes here, ever.
- **`generated/` is where every spec and role actually gets written**, each
  spec and the role it produces living together in their own folder (see
  "Role anatomy" below) rather than accumulating in flat shared
  directories - see "Staged vs. promoted" for how something eventually
  crosses from `generated/` into `collections/`.

New roles generated by `/build` MUST follow the conventions below unless
the spec explicitly overrides one.

## Collection & role naming

- Collection: `namespace.collection_name`, e.g. `cloud.aws_ops`, `infra.windows_ops`.
  Pick the namespace by domain (`cloud`, `infra`, ...), not by team or project.
- Role: `snake_case`, verb/domain-first, e.g. `manage_ec2_instance`,
  `windows_manage_iis`, `backup_create_plan`, `connectivity_troubleshooter`.
- One role = one coherent resource or capability. Composite work is built by
  composing multiple roles in a playbook, not by cramming operations into one
  giant role (see `manage_ec2_instance` + `ec2_networking_resources` combined
  in that role's README examples).

## Variable naming (strict - this is what makes roles composable)

- Every public variable is prefixed with the role name:
  `manage_ec2_instance_instance_type`, `windows_manage_iis_port`.
  Never use an unprefixed variable name in a role.
- Variables computed/registered internally (not meant to be set by the
  caller) use a **double underscore** after the role name:
  `manage_ec2_instance__ec2_instance`, `connectivity_troubleshooter_validate__next_hop`.
  This is the signal for "output/internal, not an input".
- Roles with create/delete (or similarly branching) behavior take a single
  `<role>_operation` variable (`create`/`delete`, default `create`) rather
  than separate roles per verb. `tasks/main.yml` dispatches on it:

  ```yaml
  - name: Create or delete <resource>
    ansible.builtin.include_tasks: "{{ <role>_operation }}.yml"
  ```

  or a `block` with two `include_tasks`, each gated by `when: <role>_operation == '...'`.

## Role anatomy

`/build` generates a role **staged inside the spec's own folder, under
`generated/`** - entirely outside the read-only `collections/` tree:

```
generated/<dotted-collection-name>/<SPEC_ID>/
  <SPEC_ID>.md                 # written by /spec - named after the spec's own folder, not a generic "spec.md"
  roles/<role_name>/
    meta/argument_specs.yml   # REQUIRED - formal input contract, see below
    meta/main.yml              # role dependencies, e.g. aws_setup_credentials
    defaults/main.yml          # defaults for optional variables only
    tasks/main.yml              # orchestrator: module_defaults + dispatch to operation files
    tasks/<operation>.yml       # actual implementation per operation
    templates/, files/, handlers/  # as needed
    README.md                  # REQUIRED, see shape below
  tests/integration/targets/test_<role_name>/
```

No intermediate `specs/` layer - the `<SPEC_ID>` folder sits directly
under the collection name. `<SPEC_ID>` alone already uniquely identifies
it, so a wrapping `specs/` directory (and a same-named `spec.md` file
inside a same-named folder) would just be redundant nesting.

`<dotted-collection-name>` (e.g. `cloud.aws_ops`) doesn't need to already
exist under `collections/` - it might be a brand new collection that
hasn't been created there yet. Either way, `/spec`/`/build` never write
into `collections/` itself; that folder name under `generated/` is just
where their output for that collection accumulates.

**Staged vs. promoted.** A role at `generated/<collection>/<SPEC_ID>/
roles/<role_name>/` is real, complete code - but Ansible collection
tooling (`ansible-galaxy collection build`, FQCN role resolution
`<namespace>.<collection>.<role>`, `meta/main.yml` dependency resolution)
only looks under a collection's top-level `roles/` inside `collections/`.
A staged role is **not** usable via any of that until it's *promoted*: a
human copies it (after review) into `collections/<collection>/roles/
<role_name>/` - creating the collection there first (`galaxy.yml`,
`meta/runtime.yml`, etc.) if it doesn't exist yet. `catalog.md` flags
every staged role explicitly so `/spec` and `/build` never propose
depending on one as if it were already promoted. Promotion is always a
deliberate, separate human step - never something `/spec` or `/build`
does automatically, since it's the one point where the read-only
`collections/` tree actually changes.

### `meta/argument_specs.yml` - the authoritative variable spec

Every new role MUST have one. This is what Ansible validates automatically
when the role is called. `/spec` doesn't produce this directly (its specs
are behavioral, not technical) - `/build` derives this file's contents from
the spec's Requirements/Constraints as part of its own design work.

```yaml
---
argument_specs:
  main:
    version_added: 1.0.0
    short_description: One-line summary (used verbatim in the catalog).
    description:
      - Longer description, can be multiple lines.
    options:
      <role>_operation:
        type: str
        description: Operation to perform.
        default: "create"
        choices: ["create", "delete"]
      <role>_name:
        type: str
        description: The name of the resource.
        required: true
```

### Shared credentials, not per-role auth

AWS roles depend on `aws_setup_credentials` (via `meta/main.yml`) and wrap
their tasks in:

```yaml
module_defaults:
  group/aws: "{{ aws_setup_credentials__output }}"
```

Windows roles rely on inventory/connection variables instead (no
per-role credential role) - follow whatever the target collection already
does; don't invent a second auth pattern within one collection.

### Idempotency & safety patterns actually used here

- Guard-clause checks before mutating: e.g. `manage_ec2_instance` looks up
  whether an instance with the requested name already exists and `fail`s
  with a clear message rather than silently updating it.
- `register` the result of the main resource-creating task
  (`<role>__<resource>_result`) so callers/other roles can chain off it -
  documented in the README under "the instance details are accessible via
  variable `X`".
- `no_log: true` on any task handling secrets/keys.
- `wait`/`wait_for_state`-style boolean variable when the underlying module
  supports waiting for a terminal state, defaulting to `true`.
- End create operations with an `ansible.builtin.debug` task summarizing
  what was created (id, key details) - this is the de facto "output" step.

## README.md shape (required for every role)

```markdown
# <role_name>

<1-3 sentence description - this becomes the catalog short_desc>

## Requirements
<IAM permissions / OS / collections needed>

## Role Variables
* **<role>_var_name**: (Required|Optional)
  Description. Notes on interaction with other variables, defaults, choices.

## Dependencies
- role: [<dep>](<relative-path-to-dep's-README.md>)
  <!-- A staged role's dependency link has to cross from
       generated/<collection>/<SPEC_ID>/roles/<role_name>/README.md
       all the way back to collections/<collection>/roles/<dep>/README.md
       - a different tree entirely, not just a deeper folder. Compute the
       actual relative path (or note the dependency as
       "<collection>.<dep>" in prose alongside the link) rather than
       guessing a fixed number of "../" - the depth here is easy to get
       wrong. -->

## Testing

`generated/<collection>/<SPEC_ID>/tests/integration/targets/test_<role_name>/`
- staged alongside the role for the same reason (see "Staged vs. promoted"
above), following the standard `ansible-test integration` layout (its own
`tasks/`, `defaults/`, etc.). `/build` should scaffold this directory even
if it only contains a `create + verify + cleanup` smoke test to start.
Promotion copies both the role and its test target together, into
`collections/<collection>/roles/<role_name>/` and
`collections/<collection>/tests/integration/targets/test_<role_name>/`
respectively.

## What NOT to do

- Don't write anything under `collections/` from `/spec` or `/build` -
  ever, for any reason. It's read-only reference. All output goes under
  `generated/`; promotion into `collections/` is a human's call, not a
  skill's.
- Don't invent a new variable-input format (JSON schema, argparse, custom
  YAML) - `meta/argument_specs.yml` is the only variable contract format
  used here, and it's natively enforced by Ansible.
- Don't skip the `<role>_` variable prefix "because it's obvious from
  context" - it's what lets two roles be used in the same play without
  collisions.
- Don't add a new auth/credentials mechanism inside a role that already has
  a shared credentials role in its collection.
